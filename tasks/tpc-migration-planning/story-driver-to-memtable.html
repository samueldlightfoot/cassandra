The INSERT that woke five threads

One row — partition key 'acct-42' — travels from a client driver to a memtable trie, and we count every thread it wakes and every lock it takes on the way. Then we run the same row through the planned thread-per-core design and watch what disappears. The general rule comes last. Skimming? The setup and the ⚡ boxes carry the spine.

The setup

  • An 8-core coordinator node that is also a replica. RF=3, consistency QUORUM (2 acks needed).
  • The table opts into the trie memtable (memtable: trie) — a sharded, single-writer-per-shard implementation. It is NOT the default (the shipped default inherits skiplist, conf/cassandra.yaml:823, MemtableParams.java:99).
  • Memtable shard count — how many independent slices the memtable is split into — defaults to the CPU core count: 8 shards here (AbstractShardedMemtable.java:46).
  • native_transport_max_threads (default 128) — cap on the Native-Transport-Requests pool, the threads that execute CQL requests after netty decodes them (Config.java:352, Dispatcher.java:62).
  • concurrent_writes (default 32) — worker cap for MutationStage, the pool that applies writes to the local commitlog and memtable (cassandra.yaml:758, Stage.java:47).
  • Protagonist: INSERT … WHERE account='acct-42'. Its Murmur3 token, computed with this tree’s own Murmur3Partitioner, is −121,088,327,282,641,530.

Today’s one law: any thread may execute any token’s work — so every shared structure must defend itself.

Chapter 1 · Five threads before one row is stored

covers the arrival topology: which components touch a write, and on whose thread

The driver never sends 'acct-42' to a random node. Token-aware routing — the default in modern drivers — hashes the key client-side and opens the request against a replica, so our node is both coordinator and one of the three replicas. A netty event-loop thread reads the frame and decodes it, but does not run the query: Dispatcher.dispatch submits it to the Native-Transport-Requests pool (Dispatcher.java:131). That is thread crossing #1.

An NTR thread parses the CQL, binds values — this is the first moment the token is knowable server-side — and calls StorageProxy::mutate. It fires two internode messages to the remote replicas and hands the local copy to MutationStage via stage.maybeExecuteImmediately(…) (local branch at StorageProxy.java:1918, the hand-off at :2025) — crossing #2, unless an idle-permit lets it run inline. Acks come back on internode netty threads, which dispatch them by verb to the REQUEST_RESPONSE stage (InboundMessageHandler.java:429) — crossing #3.

Checkpoint 1 — the NTR thread has fired all three replica writes. QUORUM needs 2 acks, a network round trip away. What does the thread do in the meantime? Hint: AbstractWriteResponseHandler.java:83 allocates a newOneTimeCondition() per request.

It parks. The handler blocks on a one-time Condition until 2 acks arrive or the deadline passes; reads do exactly the same (ReadCallback.java:71,126 — condition.awaitUntil(deadline)). For the entire round trip, one of the 128 NTR threads is asleep holding this request’s stack.

Generalising: any thread pool sized far above the core count (128 on an 8-core box) is a confession that its threads spend most of their life waiting, not working.

The coordinator thread is rented for sleeping: the 128-thread pool exists to absorb parked threads, not CPU work — 16× more threads than cores, so that enough of them can nap through round trips simultaneously. This nap is what the plan’s increment I3 (non-blocking coordinator) deletes — turning each await into a continuation that runs when the ack arrives.

Chapter 2 · The lock under the already-sharded memtable

covers the user’s question: why must the memtable be thread-safe today?

Pick up the local apply on MutationStage worker-17. Before touching the memtable it crosses two node-global points: the commitlog segment’s allocatePosition — a single AtomicInteger that every write on every core CASes to claim its bytes (CommitLogSegment.java:103,242-250) — and Keyspace.writeOrder, one static OpOrder for the whole node (Keyspace.java:102). Then TrieMemtable.put picks a shard: shards[boundaries.getShardForKey(key)] (TrieMemtable.java:191), a linear scan over 7 end-inclusive boundaries (ShardBoundaries.java:67-88).

token('acct-42') = -121,088,327,282,641,530 even 8-split boundaries: b[2] = -2,305,843,009,213,693,952 b[3] = 0 b[2] < token ≤ b[3] → shard 3 of 8 (single-node toy ring; a real node splits its own token ranges the same way)

Shard 3’s storage is an InMemoryTrie, and its own documentation says it is built for one writer: “this map is used in a single-producer, multi-consumer fashion: only one thread will insert items” (TrieMemtable.java:518-522). Eight shards, eight cores, single-writer tries — the data structure looks finished. So predict:

Checkpoint 2 — the memtable is sharded per core and each shard’s trie is documented single-writer. Can the shard’s write lock be deleted today? Hint: who chose worker-17 for this task — and does that chooser know what a shard is?

No — because MutationStage is shard-blind. Its 32 workers pick up whatever task is queued; two INSERTs whose tokens both land in shard 3’s range can be running on any two workers at once. So put() takes a per-shard ReentrantLock (TrieMemtable.java:513): tryLock() succeeds → uncontendedPuts++; fails → contendedPuts++ and the worker waits, with the wait time metered (TrieMemtable.java:553-563).

The lock is an adapter: it manufactures, at runtime and per write, the single-writer guarantee the scheduler declines to provide. Even cassandra.yaml:809 calls the trie memtable “a sharded single-writer solution” — the sharding is done; only the writer-assignment is missing.

2 of 32 workers are inside shard 3 at the same moment — writeLock is the only thing between them, and contendedPuts ticks up.
The memtable is already TPC-shaped — core-count shards, single-writer tries, epoch-cached boundaries. The lock exists because the scheduler is the last shard-blind layer in the write path. 2016 saw this coming: Jonathan Ellis on CASSANDRA-10993 — the real win is “not needing to use threadsafe memtables”.

Chapter 3 · The same row, rewired

covers the planned increments I1–I5 and where io_uring slots in

Run 'acct-42' through the target design. The driver changes nothing — it already routes by token. The netty event loops stay too; replacing them is an explicit non-goal (the win is storage-path affinity, not socket polling). The NTR thread also keeps its coordinator job — parse, bind, fire the replica messages. The change begins where StorageProxy hands off the local apply (StorageProxy.java:1918): instead of MutationStage, it is routed by the same ShardBoundaries.getShardForKey the memtable already uses — but now the result selects a thread, not just an array slot. Shard 3 has one owning thread with an inbox, owned by a small shard runtime that ships first as increment I0 (plain sequential() executors for the PoC; the custom MPSC drain loop arrives with I2, when the same loop must also drive the io_uring ring).

Checkpoint 3 — I1 routes every local mutation apply to its shard’s owner thread. So can the lock finally be deleted? Hint: list who else writes memtables besides the request path.

No — skipped, not deleted. The routed path covers plain mutations, but single-writer is still violated by hints, read repair, paxos commit, commitlog replay, counter and view applies — and Accord, which writes user tables from its own executor threads (TxnWrite.java:150) on this branch today. Boundary races add more: during a memtable switch, two live memtables with different ShardBoundaries accept writes at once. So I1’s step 2 is owner-check-with-lock-fallback: put() takes the lock-free path only when the current thread provably owns the shard, and falls back to the existing tryLock otherwise — self-healing for every writer routing misses. A new misroutedPuts counter, next to contended/uncontended, is the boundary-health signal.

Generalising: routing can never be assumed perfect — the fallback is a design principle, not an implementation detail. Every increment is flag-gated (read once at startup, not hot-swappable) and carries its own observable — no step asks you to believe; each one asks you to measure.

Increment I1 ships with its own proof: counters in the memtable turn “is the scheduler delivering single-writer-ness?” into a dashboard question — deploy the routing change, watch contendedPuts and the new misroutedPuts, then flip the skip-lock flag for the owner-thread fast path. This is why the plan is increments, not a big bang: each step is measurable with instruments the codebase already (or nearly) has, and gated behind a startup flag.

The rule you just watched

A data structure needs exactly as much thread-safety as its scheduler declines to guarantee. Cassandra’s memtable went shard-per-core years ago; the scheduler never followed. The shard locks, the global OpOrder, the commitlog CAS, and 128 parked coordinator threads are all adapters between shard-shaped data and a shard-blind scheduler — remove the blindness and the adapters shrink to fallbacks, one flag at a time: the fast path never pays for them, and they stay only for the writers the scheduler still doesn’t own.
SEDA — today

Work goes to whichever pooled thread is free: 128 NTR + 32 mutation + 32 read workers on 8 cores.

Ownership lives nowhere, so safety is bought at every touchpoint: lock, CAS, park. Correct — and every write pays for the generality.

TPC — target

The token picks the thread, via the same 8-way boundaries the memtable already uses. One owner per shard: its commitlog slice, its trie, its io_uring ring.

Safety by construction on the hot path; compaction/flush/streaming stay on ordinary pools.
